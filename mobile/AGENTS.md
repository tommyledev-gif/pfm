# Expo HAS CHANGED

Read the exact versioned docs at https://docs.expo.dev/versions/v54.0.0/ before writing any code.

**Pinned to SDK 54, not the latest (57), on purpose** (2026-08-16): the Play Store's Expo Go app was several SDKs behind the newly-released SDK — confirmed directly from the user's own installed Expo Go (Profile tab: client version `54.0.8`, "supported SDK 54"), not just inferred from changelogs. The project was first scaffolded on SDK 57, then downgraded twice: SDK 57 → 56 (still failed on-device — Expo's own SDK 56 changelog: *"Expo Go for SDK 56 is not available on the Apple App Store or Google Play Store. We do not have a timeline for when they will be."*) → SDK 54 (confirmed working). **Do not assume the latest SDK is safe just because `npx expo install expo@latest` type-checks and bundles cleanly** — that only proves the JS/TS code compiles, not that the Play Store's Expo Go can run it. Before ever bumping the SDK again: have whoever is testing on a real device open Expo Go's own Profile/Settings tab and report the exact "supported SDK" number it shows, and match that — don't infer it from Expo's changelogs, which can lag reality by more than one SDK cycle (56 and 57 were *both* confirmed unavailable on stores at time of writing, and 54 was the one actually installed).

If downgrading the `expo` package version leaves stale peer-dependency conflicts (`npm error ERESOLVE` on a subsequent `npx expo install --fix`), don't fight the partial install — `rm -rf node_modules package-lock.json && npm install` first, then re-run `npx expo install --fix`. Also: `expo-status-bar` does not need to be listed in `app.json`'s `plugins` array on SDK 54 — its older version's plugin resolution breaks Node's type-stripping (`ERR_UNSUPPORTED_NODE_MODULES_TYPE_STRIPPING`) if it's added there (as `npx expo install --fix` did automatically on SDK 56/57); remove it if present.
